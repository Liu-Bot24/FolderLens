# 空闲后台工作进程的内存恢复

Pro 对 `f05fde5` 提出的条件性风险，经受控原生夹具复现：后台工作进程保留内存、所有活动 lease 已释放，资源协调器进入压力状态后，新请求仍等准入；等待请求同时持有资产锁，使消费者也无法通过释放资产解除压力。

## 改动

`WorkerClient` 把请求序列锁与进程/资产锁分离。请求保持单路顺序，但准入等待不再阻止资产释放。资源压力通知回收无未释放资产的空闲后台工作进程；后续请求重新启动它。前台动画及文本会话可能含必需状态，本次不把它们按空闲后台缓存回收。

回收与请求、资产释放和关闭使用同一进程锁。关闭取消准入等待，多个 Dispose 等待同一次清理。回收任务由客户端持有并在下次请求/关闭时观察，不能把后台错误当成成功。取消请求继续按原契约回收旧工作进程，包括在准入阶段取消的情况。

## 原生夹具及结果

测试通过真实命名管道和 Job 启动单独的测试进程，分配并触碰 128 MiB 原生内存，响应后继续保留。隔离协调器以 64 MiB 软阈值判定，采样实际进程 Private Bytes，不修改生产默认阈值，也不人为制造数 GB 的整机压力。

- 实测保留约 145.5/145.8 MB 私有字节，活动 lease 为零。
- `idle-memory-native-red.trx`：后台下一请求在 3 秒界限内仍未完成；初期夹具路径/参数错误另行保留，不计入此缺陷证据。
- `idle-memory-ownership-green.trx`：无资产时回收后恢复；消费者仍持有资产时不回收、不删除文件，ReleaseAsset 不被准入锁阻塞，释放后恢复。相关 worker、动画、准入共 32 项通过。
- 新增关闭时取消准入、并行 Dispose 等待同一清理任务的回归。
- 首次全量运行 `idle-recovery-full-unit.trx` 为 313/314：锁调整使文本准入取消不再回收原进程。恢复既有取消语义后，`idle-recovery-cancellation-unit.trx` 为 314/314，通过原文本取消对照。
- 重叠收藏根中一路身份观察未知、另一路仍有效的归属保留与恢复正例也通过。
- `artifacts/pro-idle-recovery-native-final/summary.json`：完整原生 38/38 通过；`pro-idle-final-build.log`：Release 0 错误，NU1900 仅表示漏洞服务不可达。

这是后台空闲状态回收与准入活性的验证，不是实际图集或豆包语音验收。主程序、前台必要会话、系统其他进程占用所造成的持续压力仍须单独观测；本修改不建立完整的同盘 CPU/I/O/GPU 总预算。系统 WPR 采样权限不足的边界仍保留。
