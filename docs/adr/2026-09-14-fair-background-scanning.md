# 按浏览优先级推进扫描

## 问题和边界

原队列按深度降序取目录，一个大的前置分支会推迟后面所有分支。浏览切根又会取消扫描，重复打开时重复从前面的目录开始。容量刷新则逐条读取整个根的文件路径与大小。

## 决策

- SQLite 临时队列按根下的直接分支轮转，每个分支内部先浅后深。临时分支表记录最近执行顺序，不增加持久索引或迁移备份。
- 主窗口的目录范围、容量窗口当前层级可动态指定优先子树。每四次目录调度中最多三次优先，至少一次公平调度；优先范围的祖先也可提前枚举。目录完成包仍是核对删除的唯一依据。一次目录枚举完成前不强行中断并伪称完成。
- 初始完整扫描由应用生命周期持有，浏览切根只取消原页面查询、元数据请求和当前核对任务，不取消已经开始的完整扫描。最多两个根扫描同时执行，其余等待槽位；显式停止取消当前根，退出应用取消并等待全部任务结束。已有后台扫描复用任务与 epoch，重新打开时仍核验物理身份；身份变化使用新的根。
- 目录监听跟随完整扫描保留，后台变化继续记录为待核对范围。返回根后继续处理这些范围。浏览页面仍以 rootId/epoch/页面版本拒绝过时结果。
- 整根容量查询借助现有 IX_Files_Directory 索引在 SQL 中按目录聚合，只向 C# 传输目录计数/大小/未知占用数量，再统一向祖先汇总。冻结筛选结果的容量合同不变。

## 限制与验证

这不是 MFT 扫描，也不宣称已经获得资源管理器或 WizTree 的实机速度。容量仍需数据库聚合读取，没有宣称持久增量汇总；单个含大量直接文件的目录仍可能推迟下一次调度。没有新建数据库副本或全库备份，没有管理员权限依赖。

回归用例在原代码上确认：后置小目录的首文件要等到第 31 个文件；修改后要求它在前 5 个内出现。覆盖动态优先、避免其他分支饥饿、显式取消/退出/并发槽、重新打开的身份与 epoch、容量与原文件流汇总的一致性。用户禁止再次运行原生测试窗口，因此 WinUI 实际导航和真实大目录耗时未运行，不把编译或单元测试作为实机通过。
